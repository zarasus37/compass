## Work and decisions

FIN-01 consolidates tenant financial-state reads onto one server-only
Data Access Layer, `src/lib/state/financial-state.ts`, which queries
Prisma directly. It was preceded by a review-driven scope correction:
`Transaction.source` is **creation provenance**, not proof that money
arrived, so no "received"/"settled"/"available" bucket was created.

**What was actually broken.** The read surface was split. Some callers
read Prisma; four read a process-local `globalThis` store through
`src/lib/store.ts` `read*()`. Two of those sat on decision and mutation
paths:

- `src/lib/opportunities.ts` — `topOpportunities()`, which produces
  user-facing recommendations ("move this money here")
- `src/app/(app)/envelopes/actions.ts` — `listEnvelopesForAction()`, a
  server action feeding a client dropdown

On serverless a cold start makes a stale read the normal case, not an
edge. `topOpportunities` could recommend moving money that no longer
exists; the dropdown could offer vessels the database does not have.

**Three decisions, recorded as `DR-FIN-01`:**

1. **The aggregate reads inside one explicit `RepeatableRead`
   transaction.** `prisma.$transaction` alone would NOT give a coherent
   snapshot: Postgres defaults to READ COMMITTED, under which each
   *statement* may observe a different commit. A paycheck committed
   midway through the aggregate could appear in transactions and be
   missing from balances. The isolation level is explicit, not
   inherited. This is a read-consistency decision only — no writer, no
   allocation rule, no ledger behaviour changed.

2. **Settlement is unknown.** `apply-paycheck.ts` writes `source:
   "recurring"` for a cron-created paycheck and `"manual"` for a
   user-clicked one; `log-transaction.ts` writes `"manual"` for a
   user-logged entry. All are provenance. `Transaction.cleared` exists
   in the schema but is never written anywhere and defaults to `true`,
   so it carries no information either. Income therefore carries
   `confirmation: "unknown"` — asserting neither settlement nor
   failure. Nothing infers received/settled/available from `source`,
   `isPrimaMateria` or `cleared`. FIN-05 owns writer semantics plus the
   migration and backfill.

3. **The three inconsistent expense/auto predicates are NOT unified.**
   They disagree today (`mock.ts` derives `isAuto` from `source`,
   `store.ts` from a seed flag, `forecast/spending-trends.ts` uses a
   third rule in SQL). Unifying them is a financial-convention change
   and was explicitly excluded from this read refactor.

**Other behaviours deliberately preserved:**

- Existing DB-backed adapters `liveEnvelopesFromDb` and
  `liveGoalsFromDb` keep their exact output shapes (`current`/`target`
  keys, `perPaycheckCents: 0`, `description ?? ""`, `dueDay ?? 0`,
  `paidAt` as ISO string). No page had to change.
- `listEnvelopesForAction()` keeps its non-null `PlanetId` contract. The
  DB `planet` column is nullable, so an unassigned vessel falls back to
  `"jupiter"` **and logs a warning** — a visible substitution rather
  than a silent cast. This replaces the old `as PlanetId` cast that
  asserted a planet an unassigned vessel does not have.
- `topOpportunities()` predicates (`OVER_FUND_THRESHOLD`, the
  Buffer-exclusion `planet === "mars"`, `targetCents <= 0` skip) are
  untouched.
- No writes, no seeding, no period materialization from a read. A
  tenant with no rows reads empty and is never handed demo-persona
  data.

### Fixture discipline

`tests/smoke-financial-state.mjs` deliberately does NOT use
`tests/fixture.mjs`. That helper calls `sweepStaleFixtures()`, which
deletes EVERY user whose email starts with `smoke-` — including other
suites' fixtures — and its seeds use fixed primary keys so only one
fixture can hold the seeded baseline at a time. Every row in the new
smoke is created directly with a UUID this run owns, and cleanup deletes
**by those ids only**, inside a `finally`. There is no broad
`deleteMany` in the file.

## Risks and limits of this verification

- **The full smoke suite did not pass.** `pnpm smoke:all:server` exited 1
  with `smoke:integration` reporting **367 pass / 1 miss**:
  `M5: vault.bill_history_viewed event written after a bill-history
  visit — before=1 after=1`. Every other smoke file was green and the
  new FIN-01 smoke passed in-chain (42/42).
- **That miss is NOT caused by FIN-01.** The affected page,
  `src/app/(app)/vault/bills/[id]/history/page.tsx`, imports none of the
  files this task touched. The identical failure was observed in
  `_smoke_full_16.log` — before the tenant-isolation work and before
  FIN-01 — and passes in most runs. It is a pre-existing intermittent,
  now seen twice, and its mechanism is still unconfirmed. It is
  reported here rather than hidden, and is **not** claimed as fixed.
  Candidate mechanism worth investigating: the page writes the audit
  row with `await recordBillHistoryViewed(...)` at render time, and the
  page has an early 404 return BEFORE that write; under full-suite load
  a failing or contended write would yield no row while the smoke's
  `get()` still returns a response.
- **No commit, branch, worktree, push, merge or deploy was performed.**
  The work is uncommitted in the shared checkout for independent review.
- **Live/deployed behaviour was not verified.** Production was not
  touched. No CI run has executed this change; PR 12's green run covers
  the coordination work only.
- **FIN-01 is a foundation step, not a claim of financial correctness.**
  It proves reads are durable, tenant-scoped and consistent. It does not
  prove the financial model is right, that ledger reconciles
  (FIN-02), or that income actually arrived (FIN-05, BANK-01).
- **Remaining process-local readers** — `/transactions` and
  `/calendar` display pages, `vault/mock-data.ts`, and the memory
  seeders — still read `store.ts`. Deferred deliberately: converting
  them changes visible read behaviour and belongs in its own reviewed
  scope.
- **Advisor simulate/paycheck paths** still use legacy memory state.
- **`Transaction.cleared` remains an unwritten dead column.** FIN-01
  passes it through untouched; wiring it changes writer semantics and
  belongs to FIN-05.
- **`planetHint` fallback.** `listEnvelopesForAction()` substitutes
  `"jupiter"` for an envelope with no valid planet, to preserve its
  non-null contract. It logs a warning when it does this. Seeding and
  `envelope-db.ts` always set a real planet, so this is a defensive
  edge, but a reviewer should confirm the substitution is acceptable
  versus widening the action's return type.
- **Not exercised at runtime under a server.** The 42-check smoke runs
  `tsx` directly against Prisma, not through a Next server. The
  in-chain run in `smoke:all:server` provides the integrated check;
  that result is recorded in the final report to the user.
- **A reviewer must confirm the RepeatableRead boundary is adequate.**
  `Promise.all` inside one interactive transaction issues concurrent
  statements on one connection; correctness depends on that connection
  being serialised, which is normal for `pg` but worth confirming
  against the installed adapter version.

## Recommendation

Ready for independent review. The scope was held to reads; the two
decisions most worth scrutinising are the `RepeatableRead` boundary and
the `planetHint` fallback described above.
