## Why two projects exist

xKryptic noticed on 2026-09-26: *"I notice that there is two compass sites, one specific to MOM and the other just general. Why is it?"* The inspection below answers that — **they are NOT duplicates**, they are **separate environments** with different state, different admin users, different databases, and different build commands.

- **`compass`** is the operator's preview/development environment (12 Sep 2026, "15 days ago" per Vercel). It has the full vault/crypto config + Ollama config + Neon direct proxy + a default `next build` (no migrations applied at build).
- **`compass-mom`** is mom's separate staging environment (23 Sep 2026, "4 days ago" per Vercel). It has its own database, its own admin user, no vault/crypto (mom isn't a vault user — that's the operator's later feature), and a custom build command that runs `pnpm prisma migrate deploy && pnpm seed:admin && pnpm build` so the database is always migrated + admin seeded on every prod deploy.

Both auto-deploy from `main` on push — so any commit to `main` (e.g., `de72028` Cluster 7.43) reaches BOTH environments. This is correct: a single source of truth, two deployment targets with different configs.

## Recommendation (pending operator confirmation)

**Do NOT consolidate.** The two projects are deliberately separate environments with different state. Deleting either would either (a) lose mom's deployed database + admin user, or (b) lose the operator's preview environment with its full vault/crypto/Ollama config.

**If `compass-mom` is meant to be the canonical production environment** (which it sounds like — it has the production-safe build command with migrations), the natural future direction is:

1. Promote `compass-mom` to be the only auto-deploy target on push to `main`.
2. Migrate the operator's preview-only changes (vault config, Ollama URLs, CRON_SECRET) onto `compass-mom` as separate variables.
3. Update `.vercel/project.json` to point at `compass-mom`'s projectId (`prj_FDWTzM8N0tB7TcGI20D5WAKEztxI`).
4. Disconnect `compass` from the GitHub repo so it stops auto-deploying (but DON'T delete it — the operator's preview environment is useful for testing changes against the operator's own DB without affecting mom).

If you want to go that direction, **before any disconnect**: copy all 8 `compass`-only env vars from production into `compass-mom`'s production env. Then disconnect `compass` from GitHub. Then update `.vercel/project.json`. Then optionally delete `compass` after confirming nothing is referencing it.

**This is an operator decision** — none of the above has been executed. The auto-push rule (xKryptic 2026-09-26) covers commits, not Vercel project state changes; deletion / disconnect of a deployment target is the kind of action that needs explicit confirmation.

## Reproducing this snapshot

```sh
# From the Compass workspace root:
vercel whoami                                       # confirm logged in
vercel project ls                                   # both projects visible
vercel project inspect compass                      # project 1 metadata
vercel project inspect compass-mom                  # project 2 metadata
vercel domains ls                                   # custom domains (1 total: sovereignmonad.xyz)
vercel env ls production --project compass --format json   > /tmp/compass-production.json
vercel env ls preview --project compass --format json      > /tmp/compass-preview.json
vercel env ls development --project compass --format json  > /tmp/compass-development.json
vercel env ls production --project compass-mom --format json   > /tmp/compass-mom-production.json
vercel env ls preview --project compass-mom --format json      > /tmp/compass-mom-preview.json
vercel env ls development --project compass-mom --format json  > /tmp/compass-mom-development.json
```

The output files have `key`, `type` (`sensitive` for env vars with redacted values; `plain` for unredacted), and per-environment targeting (production / preview / development). Values are redacted by Vercel when reading via CLI — `vercel env pull` is the way to get plain values into a local `.env.local` (already used in this repo's `.env*` setup).
