| `compass-mom` | `pnpm prisma migrate deploy && pnpm seed:admin && pnpm build` | Unchanged. Also seeds the admin user on every prod deploy. |

### Why `prisma generate` moved into `pnpm build`

The generated Prisma client is **gitignored** (`/src/generated/` in
`.gitignore`) because it is a ~13 MB build artifact, not source. The
schema (`prisma/schema.prisma`) is the source of truth.

So `prisma generate` **cannot** be a standalone CI/Vercel step that
runs before the build — nothing in the checkout is generated yet, and
Vercel builds from a clean tree. It has to happen *inside* the build,
which is why `pnpm build` is `prisma generate && next build`
(`package.json`).

**Consequence for local work:** a fresh clone, or a `git clean`, will
fail `pnpm build`/`pnpm tsc` until `pnpm db:generate` has run. Never
"fix" that by committing `src/generated/`.

### Why migrations must stay in the build command

Both projects share the repo but point at **different databases**. The
migration step is what keeps each environment's schema current on every
deploy from `main`. Removing it from the build command means a deploy
ships app code against a stale schema.

## Why two projects exist

xKryptic noticed on 2026-09-26: *"I notice that there is two compass sites, one specific to MOM and the other just general. Why is it?"* The inspection below answers that — **they are NOT duplicates**, they are **separate environments** with different state, different admin users, different databases, and different build commands.

- **`compass`** is the operator's preview/development environment (12 Sep 2026, "15 days ago" per Vercel). It has the full vault/crypto config + Ollama config + Neon direct proxy + a default `next build` (no migrations applied at build).
- **`compass-mom`** is mom's separate staging environment (23 Sep 2026, "4 days ago" per Vercel). It has its own database, its own admin user, no vault/crypto (mom isn't a vault user — that's the operator's later feature), and a custom build command that runs `pnpm prisma migrate deploy && pnpm seed:admin && pnpm build` so the database is always migrated + admin seeded on every prod deploy.

Both auto-deploy from `main` on push — so any commit to `main` (e.g., `de72028` Cluster 7.43) reaches BOTH environments. This is correct: a single source of truth, two deployment targets with different configs.

## Vault health gate (`VAULT_ENABLED=1`) — added 2026-10-06

### The bug it fixes

`/api/health` used to require a real signer in **any** production
deployment:

```ts
prodReady: isProd ? hasRealSigner : true   // BEFORE
```

`compass-mom` runs `NODE_ENV=production` but has no vault config at all,
so `hasRealSigner` was `false` → `prodReady: false` → **`allOk: false` →
HTTP 503**. `compass-mom` sat degraded while `compass` was correctly 200,
even though nothing was wrong with it: mom simply isn't a vault user.

Worse, a 503 from `/api/health` is what CI-style readiness probes and
uptime monitors read. A healthy non-vault deployment was reporting itself
as broken.

### The fix

The vault check is now an **explicit opt-in**, so "I don't have a vault"
is a valid, healthy state and "I have a vault and it's misconfigured" is
still loud:

```ts
const vaultEnabled = process.env.VAULT_ENABLED === "1";
ok:        vaultEnabled ? !!process.env.VAULT_CHAIN_ID : true,
prodReady: vaultEnabled && isProd ? hasRealSigner : true,
```

`checks.vault.enabled` is reported either way, so the payload still shows
the real chain/signer config — it's just not a gate unless asked.

### Which project sets it

| Project | `VAULT_ENABLED` | Expected |
|---|---|---|
| `compass` (Production) | `1` | 200, and **stays fail-loud** if the signer or chain id goes missing |
| `compass-mom` | *unset* | 200, vault reported as `enabled: false`, never 503s for vault reasons |

### ⚠ Order of operations (this matters)

**Ship the code change to `compass` BEFORE setting `VAULT_ENABLED=1`.**
The code change *loosens* the gate, so shipping it first cannot make
`compass` go red. Setting the env var first — i.e. pushing code that
reads `VAULT_ENABLED` while the var is absent — would leave `compass`
silently ungated in the interim, and a later redeploy could flip it.

### Also fixed: the hardcoded service name

The response reported `service: "compass"` on **both** projects, so
`compass-mom`'s health output claimed to be `compass`. It now reads
`process.env.VERCEL_PROJECT_NAME ?? "compass"`, which Vercel sets per
project.

### Known limit

CI runs the smokes against `pnpm dev` with `NODE_ENV=development`, so
**none of this is covered automatically** — `isProd` is always false in
CI. Tracked as a ticket in `HANDOVER-TEST-INTEGRITY.md` ("Known open,
deliberately not fixed").

## 🔴 `compass-mom` is broken in two ways beyond the vault gate (found 2026-10-06)

Fixing the vault gate does **not** make `compass-mom` return 200. Two
independent problems remain, both confirmed against live infrastructure.

### 1. Deploys to `compass-mom` are FAILING — `CRON_SECRET` whitespace

The push of `46536c2` deployed **Ready** on `compass` but **Error** on
`compass-mom` (build duration 10s):

```
Error: The `CRON_SECRET` environment variable contains leading or trailing
whitespace, which is not allowed in HTTP header values.
```

Vercel rejects the value at `vercel build`, before any app code runs.
`CRON_SECRET` on `compass-mom` was created **2 days ago** (23 days earlier
on `compass`, where it is well-formed). **Every `compass-mom` deploy since
then has failed**, so the live deployment is ~4 days old and predates the
vault-gate fix entirely.

**Fix:** re-set `CRON_SECRET` on `compass-mom` (Production) with **no
leading/trailing whitespace** — e.g. a fresh `openssl rand -hex 32`.
Do **not** just delete it: `src/lib/cron-auth.ts` fails **closed** in
production, so with it unset all three `/api/cron/*` routes return
`503 {"error":"cron not configured"}` and the `vercel.json` cron jobs
silently do nothing.

### 2. `compass-mom`'s Mavis key is rejected (401)

Even with a successful build, `allOk` in production also requires
`ai.ok`. `compass-mom` currently reports:

```
ai.ok = false
Mavis internal /v1/chat/completions -> HTTP 401:
  {"type":"authorized_error","message":"token is unusable (1004)","http_code":"401"}
```

"token is unusable (1004)" means the key itself is rejected — not a
network or provider outage. `compass` is unaffected (`ai.ok = true`,
"Reachable"); the two projects hold **different** `MAVIS_API_KEY` /
`COMPASS_AI_MAVIS_API_KEY` values, and only `compass`'s was rotated.

**Fix:** set a current Mavis key in **both** `MAVIS_API_KEY` and
`COMPASS_AI_MAVIS_API_KEY` on `compass-mom` (Production).

### 3. Also note: the production alias is behind Vercel Authentication

`https://compass-mom-sovereign-monad-ecosystem.vercel.app` returns
**HTTP 200 with a Vercel login page** (`<title>Login – Vercel</title>`,
`content-type: text/html`) to unauthenticated requests. The plain alias
`https://compass-mom.vercel.app` serves the app unauthenticated.

Practical consequence: an unauthenticated probe of the production alias
looks "200 OK" while telling you nothing about the app. Monitor
`compass-mom.vercel.app`, or expect to authenticate.

## Recommendation (pending operator confirmation)

**Do NOT consolidate.** The two projects are deliberately separate environments with different state. Deleting either would either (a) lose mom's deployed database + admin user, or (b) lose the operator's preview environment with its full vault/crypto/Ollama config.

**If `compass-mom` is meant to be the canonical production environment** (which it sounds like — it has the production-safe build command with migrations), the natural future direction is:

1. Promote `compass-mom` to be the only auto-deploy target on push to `main`.
2. Migrate the operator's preview-only changes (vault config, Ollama URLs, CRON_SECRET) onto `compass-mom` as separate variables.
3. Update `.vercel/project.json` to point at `compass-mom`'s projectId (`prj_FDWTzM8N0tB7TcGI20D5WAKEztxI`).
4. Disconnect `compass` from the GitHub repo so it stops auto-deploying (but DON'T delete it — the operator's preview environment is useful for testing changes against the operator's own DB without affecting mom).

If you want to go that direction, **before any disconnect**: copy all 8 `compass`-only env vars from production into `compass-mom`'s production env. Then disconnect `compass` from GitHub. Then update `.vercel/project.json`. Then optionally delete `compass` after confirming nothing is referencing it.

**This is an operator decision** — none of the above has been executed. The auto-push rule (xKryptic 2026-09-26) covers commits, not Vercel project state changes; deletion / disconnect of a deployment target is the kind of action that needs explicit confirmation.
